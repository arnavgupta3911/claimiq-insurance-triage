# Model Card: ClaimIQ Review-Priority Classifier

## Purpose

This is a proof-of-concept classifier that estimates whether a (synthetic) insurance claim should be prioritised for human review. Its intended use is to **reorder a review queue** in a demonstration app. It isn't intended to approve, deny or price claims, and it must not be used with real customer data or for real decisions.

I built it to show an end-to-end ML workflow (data, training, evaluation, serving, storage, UI) applied to an operational insurance problem.

## Data

5,000 claims generated by `src/generate_data.py` with a fixed seed (42). No real data was used.

| Field | Generation |
|---|---|
| `claim_amount` | Log-normal (mean of log 8.3, sd 0.7), clipped to $200–$50,000 |
| `claim_type` | Medical 55%, Disability 25%, Life 20% |
| `policy_age_months` | Uniform integer 1–240 |
| `documents_required` | Uniform integer 2–6 |
| `documents_submitted` | `documents_required` − Binomial(`documents_required`, 0.18) |
| `days_since_incident` | Uniform integer 0–180 |
| `previous_claims` | Poisson(0.8), clipped 0–7 |

**How the labels were made.** `requires_review` is simulated, not observed:

```
score = -2.5
        + 0.000065 × claim_amount
        + 0.75     × documents_missing
        + 0.008    × days_since_incident
        + 0.20     × previous_claims
        − 0.009    × policy_age_months
        + 0.25     × [claim_type == Disability]
        + Normal(0, 0.5)
requires_review ~ Bernoulli(sigmoid(score))
```

These coefficients are invented and do not represent real insurance rules. The noise term and Bernoulli sampling make the label deliberately not fully predictable. Overall review rate: 19.3%. Data checks: no missing values, and no rows where submitted documents exceed required documents.

**What this means for interpretation:** the project tests whether the pipeline can recover patterns from a controlled simulation. It does **not** show that the model can identify genuinely problematic real-world claims.

## Features

`claim_amount`, `claim_type`, `policy_age_months`, `documents_submitted`, `documents_required`, `days_since_incident`, `previous_claims`.

The `claim_id` and the target are excluded, and no information about future review decisions is used as an input. `documents_missing` isn't given directly. The model has to infer it from the two document counts.

## Training setup

- **Split:** 80% train (4,000) / 20% test (1,000), stratified on the label, `random_state=42`.
- **Preprocessing:** `StandardScaler` on numeric features and `OneHotEncoder` on `claim_type`, inside a scikit-learn `Pipeline` so they're fitted only on training data.
- **Algorithm:** `LogisticRegression` (L2, C=1.0, `max_iter=1000`). Chosen because it suits binary classification, trains quickly, outputs probabilities, and its coefficients are directly inspectable.
- **Baseline:** `DummyClassifier(strategy="most_frequent")`, which always predicts "no review".

## Results (test set)

| Metric | Model @ 0.5 | Baseline |
|---|---|---|
| Accuracy | 0.816 | 0.807 |
| Precision | 0.636 | 0.000 |
| Recall | 0.109 | 0.000 |
| F1 | 0.186 | 0.000 |
| ROC AUC | 0.747 | 0.500 |

Confusion matrix @ 0.5: TN 795, FP 12, FN 172, TP 21.

Threshold trade-off:

| Threshold | Precision | Recall | F1 | Flagged |
|---|---|---|---|---|
| 0.3 | 0.435 | 0.466 | 0.450 | 20.7% |
| 0.4 | 0.479 | 0.233 | 0.314 | 9.4% |
| 0.5 | 0.636 | 0.109 | 0.186 | 3.3% |
| 0.6 | 0.643 | 0.047 | 0.087 | 1.4% |
| 0.7 | 0.500 | 0.010 | 0.020 | 0.4% |

**Findings**
1. The model beats the majority-class baseline on ROC AUC, precision, recall and F1. Its accuracy gain is small (+0.9 points), because accuracy is dominated by the 81% majority class.
2. At the default 0.5 threshold, the model catches only about 11% of review cases. A threshold near 0.3 balances precision and recall much better (F1 0.45). The app's default stays at 0.5 to match the project brief, and a slider lets users explore the trade-off.
3. These thresholds were compared on the test set, so the table is descriptive rather than an unbiased estimate for a tuned threshold. A proper choice needs a separate validation set.

The signs match the simulation that produced the labels. That's a sanity check on the pipeline, not evidence about real claims. The two document coefficients are near-equal and opposite because together they represent "documents missing". These coefficients show **associations in synthetic data**. They aren't causal effects, and they don't fully explain any individual prediction.

## Limitations

- **Synthetic data:** performance says nothing about real claims. Real claims data would have different distributions, missing values, data-entry errors and label noise from inconsistent historical decisions.
- **Fairness:** there are no demographic attributes in this data, so no fairness analysis is possible. With real data, features such as claim history or policy age can act as proxies for protected characteristics, and historical review decisions can encode bias. A disparate-impact assessment would be required before any use.
- **Privacy:** the app stores claims in a local, unauthenticated SQLite file. Real deployments would need access control, encryption, retention policies and compliance with privacy regulation.
- **Calibration:** scores weren't calibrated against real outcomes and shouldn't be read as real probabilities.
- **Threshold:** 0.5 is a demonstration default, not an operational policy.
- **Simple model:** logistic regression assumes a linear relationship in log-odds. That happens to match how this data was simulated, which flatters it relative to messier real-world data.
- **Drift:** there's no monitoring, so a real model would degrade silently as claim patterns change.

## Why human review remains essential

The model only prioritises; it never decides. Even in this simulation, it misses most review cases at the default threshold and wrongly flags others. Real claims involve context the model can't see, such as documents' contents, medical details and conversations with the claimant. Insurance decisions also carry legal, ethical and regulatory accountability that has to rest with people. Any real version of this tool would need human reviewers to see every claim, override the queue freely, and have their decisions fed back to evaluate and improve the model.
